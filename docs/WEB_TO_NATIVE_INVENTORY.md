### 8.2 Reuse recommendation, not a mandated rewrite

Keep the existing Node/Colyseus deployment unchanged for the web game. Reuse its invitation UX, catalog validation, health/error concepts and room-state requirements where useful. Its gameplay server and wire schema are not a native room-discovery backend as-is.

For native, a small supporting service must eventually map an invite/room to a reachable Rust match server and advertise map/gameplay compatibility, admission state and expiry. Registration/heartbeat, host ownership, secure join credentials and public-host reachability are **new contracts**, not existing APIs. The implementation could adapt the current Node service or be a small Go service consistent with the approved learning/architecture direction. This audit chooses no implementation language rewrite or provider. Preserve the established preference for Go supporting services while evaluating actual reuse at that later milestone.

Authoritative movement, fuel, collision, firing, damage, lifecycle and match outcomes stay in the shared Rust core/server. Go/HTTP may discover rooms or handle later accounts/profiles; gameplay packets go directly to Rust (or an appropriate relay), never via account API calls per update. WebSocket/TCP and Renet/netcode UDP are not compatible transports. Public internet hosting requires a separately designed NAT/firewall/relay/admission solution; a Cloud HTTP/WebSocket endpoint is not evidence of UDP hosting support. Current player-hosted games remain casual/trust-limited; secure tokens alone do not make player-controlled servers trusted score authorities.
